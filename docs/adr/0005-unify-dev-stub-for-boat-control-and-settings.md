# Extend the Settings stub into a unified dev stub covering boat control too

`docs/adr/0004-settings-stub-for-local-dev.md` gave the Settings page a local backend, but the Control UI's boat-control channel (a WebSocket on `:81`, see `MiniKenterpriseCode/Parser.h`) had no equivalent — with nothing listening on `:81` during `npm run dev`, the socket fails silently and the UI just sits in its offline/error state, indistinguishable from a real firmware bug. That ambiguity made it hard to separate frontend bugs from backend/hardware bugs while developing without a flashed board.

We replaced `settings-stub.js` with `minikenterprise_frontend/dev-stub.js`, a single dev-only Node process that mocks both wire protocols the Control UI speaks: the existing `/api/settings` HTTP mock, unchanged, plus a new WebSocket mock on `:81` (using the `ws` package) that decodes and logs every incoming control command to the terminal, replies to `Heartbeat` so the UI's online/offline state behaves correctly, and pushes slowly drifting `Status` messages so battery/network indicators visibly react. The control mock reuses `Parser`/`Communication_Commands` from `src/my_modules/parser.js` directly rather than reimplementing the wire format, so the mock can't drift out of sync with the real frontend protocol logic.

This gives one command (`npm run dev-stub`) and one terminal to fully develop and debug the Control UI — both pages, both channels — without hardware, and to watch exactly what the frontend sends before deciding whether a bug is a frontend, backend/firmware, or hardware issue. As before, it mirrors protocol shape only (no EEPROM persistence, no real motor/LED behavior, no restart semantics) — a test double, not a second implementation.
